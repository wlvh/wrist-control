# 电脑、手表、手机的首次真机联调记录

这是一组设备上的实际观察：macOS 26.6.2、Xcode 27、watchOS 27.0，以及与手表配对的 iOS 27.0 手机。它记录了本次走通的路径和遇到的故障，不保证别的系统与网络组合表现相同。设备名称、序列号、签名团队、代理地址和逐事件日志没有放进公开仓库。

## 先分清三条连接

| 目的 | 本次涉及的设备 | 看到什么才算走通 |
| --- | --- | --- |
| 开发配对 | 手机与手表原有系统配对；Mac 的 Xcode 识别手机和真实手表 | Device Hub 中出现真实手表，且与同型号模拟器分开 |
| 开发安装 | Mac 的 Xcode 通过本地网络与手表建立安装连接 | 针对真实手表的签名包安装成功，应用能够启动 |
| 阅读控制 | 手表前台应用通过 CoreBluetooth 直连 Mac 应用 | 电脑自己的文章窗口收到表冠滚动、停手和按钮标记 |

手机在本轮帮助完成开发设备的配对与信任。腕控没有手机应用目标，运行时也不经手机转发动作。代码里 Mac 用 `CBPeripheralManager` 提供蓝牙服务，手表用 `CBCentralManager` 在前台寻找服务；这条运行时链路不需要为应用申请本地网络权限。它与 Xcode 安装应用时使用局域网是两回事。实现入口见 [Mac 蓝牙服务](../MacApp/MacBluetooth.swift)、[手表连接与表冠输入](../WatchApp/WatchModel.swift)。

## 本次怎样完成开发配对

1. Mac 安装了与目标系统匹配的正式版 Xcode。配对的手机和手表分别开启开发者模式并确认系统提示；密码和信任确认只在设备的系统界面处理。
2. 本次先让手机与 Mac 建立开发连接，再在 Xcode 的 Device Hub 选择 **Pair Nearby Device…**。手表开发者模式页面出现了“Pair with Mac”入口，完成后 Device Hub 把真实手表列为可用设备。[苹果的 Device Hub 说明](https://developer.apple.com/documentation/xcode/pairing-your-devices-with-your-mac)也列出无线配对路线，并要求配对的手机和手表都开启开发者模式；手机使用数据线只是本次采用的路径。
3. 选择构建目标时核对是真实设备。列表里同时有同系列手表模拟器；模拟器名称相似，不能代替真机安装证据。

Xcode 中显示“已配对”，只证明开发设备能被识别。它不证明签名包已安装，也不证明腕控的蓝牙控制链路已建立。开发者模式是这次通过 Xcode 安装测试包的条件，不应被写成未来正式安装体验的普遍要求。[苹果对开发者模式的说明](https://developer.apple.com/documentation/xcode/enabling-developer-mode-on-a-device)。

Xcode 还曾在云同步目录读取项目权限文件时卡住；将工作仓库移到本地普通目录后恢复。这是本机文件读取问题，不能据此判断手表配对或蓝牙失败。

签名是另一道独立门槛。本次曾有证书可见，但签名仍在钥匙串授权处停住；保留原钥匙串后，在用户自行设置密码的独立开发钥匙串里生成了新证书与私钥。只有实际签名校验通过、安装许可包含这块手表，才继续安装。证书、私钥、团队编号和安装许可均不进入公开仓库。

## “同一 Wi-Fi”仍安装超时的原因

真实手表已配对且开发者模式开启，Mac 与手表也确认连接同一 Wi-Fi；Xcode 图形界面和 `devicectl` 安装仍报 `CoreDeviceError 4000 / RemotePairingError 1001`，提示建立开发连接超时。此时手表应用尚未安装，故障不能算作腕控运行时蓝牙失败。

本机网络记录进一步显示：用于发现设备的 Bonjour 连接走进系统代理，随后出现 `Proxy failed`。Mac 的代理例外已有局域网 IP 范围，却没有本地域名 `*.local`。得到设备拥有者许可后，我们只临时增加这条例外，保留原有代理开关和例外；随后的手表安装与前台启动均成功。每次试验结束都恢复设置，最终完整代理配置与试验前一致。macOS 支持针对主机或域名设置代理例外，见[苹果代理设置说明](https://support.apple.com/guide/mac-help/mchlp25912/mac)。

这是一条有前后对照的本机故障线索。遇到类似超时时，先核对手表是否解锁、真实 Wi-Fi 连接和开发者模式，再查看 Mac 的代理路由及连接错误。根据证据区分配对、签名和安装连接故障，避免未经定位就重置钥匙串。

联调中还有一次容易误判的现象：Mac 同时运行了安装版与构建目录里的副本。手表已经在控制安装版，但代理看着没有输入的副本窗口，以为“连接上却没滚动”。关闭副本、核对进程路径后，安装版显示了实际滚动与标记。电脑窗口标题相同，判断目标时应看运行实例和该窗口的处理计数。

## 应用运行后，怎样判断恢复与延迟

首轮真机记录里，电脑处理了 537 条滚动、25 条停手和 3 条标记；两端有 376 条消息按会话与序号对应，其中 375 条是控制动作，1 条是 hello。它证明基础蓝牙输入到测试窗口输出曾工作。消息对应不代表屏幕已经画出，也不能拿手表和电脑各自的时间戳相减来声称精确延迟；画面响应需要同一镜头拍到表冠和屏幕。

手表应用进入非活动状态时，当前代码会主动停止扫描、清空未发意图并断开；手表保留的日志中有三次 `app_policy_disconnect_nonactive`。所以放下手腕后需要重连，首先要检查这条应用策略的影响。是否必须唤醒屏幕、重新进入应用，以及停顿后第一下表冠能否生效，还需要按正常姿势读文章验证。

电脑上的“导出诊断”已验证能保存 JSON 并在访达选中文件；那次按钮检查只取得电脑日志。首次双端原始日志是分别从两台设备的本地存储取回后合并，**尚未证明手表在线时的原生蓝牙双端导出可用**。完整阅读、30 秒／1 分钟／3 分钟停顿和重启测试，应先保存阅读记录，再让新进程产生新日志。[公开证据边界](../evidence/STATUS.md)保留了每层证据可证明的范围。


## 0.2 通用滚轮联调补充

新增应用内认证后，Mac 使用数据保护钥匙串保存设备密钥，需要 `keychain-access-groups` 和相应开发描述文件。旧测试窗口版本只靠开发证书签名的结果，不能证明新权限已获得。本轮检查了新产物的内嵌描述文件、访问组匹配和严格签名校验，并观察到 Mac 密钥导入成功、临时导入文件被删除、实际无交互读取返回成功。

Xcode 的命令行报告 `No Accounts` 时，界面也显示未登录；设备拥有者重新登录后，自动生成 Mac 描述文件成功。没有因此重置旧钥匙串或更换已有证书私钥。

真机应用可以安装成功而启动失败。本轮 Watch 安装及应用容器文件复制成功，随后启动因 `Locked` 被系统拒绝；应让使用者解锁并进入应用，不能把安装回执算作应用已运行。`devicectl device process launch` 的设备和日志参数要放在 bundle 标识之前，否则会被解释为传给应用的参数。

安装仍仅临时增加本地设备的代理例外，命令无论成功失败都恢复进入操作前的设置；复核恢复成功。蓝牙运行本身仍不依赖 Wi-Fi 或手机转发。
